# F20 — Mejora DDJJ de salud: respuestas Sí/No y detalle condicional

> Ficha de mejora correctiva sobre F16, registrada como F20 para mantener la trazabilidad SDD.
> Peso máximo permitido: 8 KB.

---

## Objetivo

Reemplazar los checkboxes de la DDJJ de F16 por un panel de respuestas explícitas **Sí/No** para cada condición y exigir una descripción únicamente cuando alguna respuesta sea afirmativa. Si todas las respuestas son “No”, el operador puede continuar sin descripción.

## Alcance

- Panel de cinco preguntas con radios **Sí** y **No**:
  - preexistencias,
  - internaciones en los últimos 12 meses,
  - embarazo actual,
  - medicación crónica,
  - discapacidad declarada.
- Cada pregunta debe responderse explícitamente; no se acepta “sin responder”.
- Campo de descripción visible para todo el panel:
  - obligatorio si al menos una respuesta es “Sí”;
  - opcional si todas son “No”.
- La confirmación expresa de la DDJJ sigue siendo obligatoria.
- El backend mantiene el contrato de F16: booleanos, `detalle` obligatorio si hay positivos y `declaracion_confirmada=true`.
- Se actualizan los tests de UI para validar radios, respuestas incompletas y detalle condicional.

## Fuera de alcance

- Una descripción separada por cada condición o por cada integrante.
- Adjuntar estudios, certificados o documentación.
- Cambiar la regla R7 ni el modelo de datos.
- Recargos, carencias o evaluación médica automática.
- Cambiar la API o las ventas ya guardadas.

## Planificación técnica y arquitectura

- **Estado JS `ddjj`:** cada indicador usa `true`, `false` o `null` (sin responder). El valor inicial es `null`.
- **`inicializarDDJJ`:** enlaza radios `name="ddjj-<campo>"` con valores `si`/`no`, y restaura la selección desde el estado o desde la venta editada.
- **Validación:** `ddjjCompleta()` exige que los cinco valores sean booleanos; el detalle se valida solo si `ddjjConIndicadores()` es verdadero.
- **Payload:** convierte las respuestas a booleanos; la validación previa impide enviar `null`.
- **Descripción:** el textarea permanece visible; el texto de ayuda cambia entre “obligatoria” y “opcional”.
- **Backend:** sin cambios de modelo, migración ni regla R7. `SaludIn` ya exige confirmación y detalle cuando hay indicadores.
- **Privacidad:** la DDJJ sigue fuera de `sessionStorage` y el detalle solo se muestra en el legajo.

## Tests y casos borde

- Todas “No” + confirmación + sin descripción → se puede avanzar.
- Alguna “Sí” + sin descripción → error de validación y no avanza.
- Alguna “Sí” + descripción → se puede avanzar.
- Pregunta sin responder → error y foco/aviso.
- Sin confirmación → error.
- Edición de una venta F16: las respuestas Sí/No se restauran correctamente.
- La API existente sigue aceptando el payload de F16.
