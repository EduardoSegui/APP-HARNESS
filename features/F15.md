# F15 — Ver, reabrir y editar ventas por etapas

> Ficha de especificación y planificación de acuerdo al ciclo SDD (7 pasos).
> Peso máximo permitido: 8 KB.

---

## Objetivo

Permitir que el operador consulte un legajo desde el panel y lo reabra en el wizard para corregir datos, agregar o quitar adherentes, cambiar de plan, medio de pago o instrumento. Las ventas `PENDIENTE_VERIFICACION` y `OBSERVADA` podrán volver a auditarse; las `APROBADA` serán inmutables.

## Alcance

- Acción **Ver / Editar legajo** en cada fila del panel `/ventas`.
- Ruta HTML `GET /ventas/{id}/editar` que renderiza el wizard en modo edición con todos los datos precargados.
- Ruta API `PUT /api/ventas/{id}` que reemplaza el legajo completo en una transacción.
- Edición libre de las tres etapas: titular y domicilio, adherentes, plan, medio de pago e instrumento.
- Recalculo server-side de `subtotal_base`, `descuento_porcentaje` y `precio_total`.
- Al guardar: limpiar `observaciones`, volver a `PENDIENTE_VERIFICACION` y conservar timestamps de creación.
- Bloqueo de edición para `APROBADA` con HTTP `409`.
- Datos de pago: si el medio no cambia y se omite el instrumento, se conservan los metadatos enmascarados; si cambia a tarjeta/CBU o se envía un instrumento nuevo, se reemplazan.
- Vista de solo lectura / comprobante para `APROBADA`.

## Fuera de alcance

- Edición de ventas `APROBADA`; se considerará una feature posterior de rectificación con auditoría.
- Borrado físico de ventas.
- Control de concurrencia multiusuario con bloqueo optimista; v1 usa última escritura ganadora.
- Historial de cambios y línea de tiempo: se planifica en F18.
- Roles y permisos de operador: se planifican en una feature de seguridad posterior.

## Clarificación y ambigüedades resueltas

> **Paso 3 SDD: Clarificación**

- [x] **Estados editables:** `PENDIENTE_VERIFICACION` y `OBSERVADA`. → **Decisión:** aprobadas quedan inmutables.
- [x] **Alcance de la edición:** ¿solo datos básicos o legajo completo? → **Decisión:** legajo completo, retrocediendo y avanzando por las tres etapas.
- [x] **Estado posterior:** ¿se conserva `OBSERVADA`? → **Decisión:** se limpia y vuelve a `PENDIENTE_VERIFICACION` para una nueva auditoría.
- [x] **Instrumento en edición:** ¿se puede conservar la tarjeta/CBU enmascarada? → **Decisión:** sí, si no cambia el medio; si cambia o se envía uno nuevo, se revalida y reemplaza.
- [x] **Concurrencia:** → **Decisión:** última escritura gana en v1; el historial y los bloqueos se postergan.
- [x] **Venta inexistente:** → **Decisión:** `404`; venta aprobada: `409`; payload inválido: `422`.

## Criterios de aceptación

- [ ] El panel muestra la acción de edición solo para ventas pendientes u observadas.
- [ ] El wizard de edición precarga titular, domicilio, adherentes, plan, medio de pago e instrumento enmascarado.
- [ ] Se puede agregar, quitar y modificar adherentes y cambiar de plan.
- [ ] `PUT /api/ventas/{id}` recalcula el desglose y actualiza en una sola transacción.
- [ ] Una venta editada vuelve a `PENDIENTE_VERIFICACION` y sus observaciones quedan en `null`.
- [ ] Una venta `APROBADA` no puede editarse y responde `409`.
- [ ] Los errores de validación responden `422` y no dejan cambios parciales.
- [ ] `uv run pytest` y `./init.sh` pasan al 100%.

## Planificación técnica y arquitectura

- **Servicio `ventas.py`:** `actualizar_venta(db, venta_id, datos)` con bloqueo de estado, reemplazo de integrantes, recálculo y commit atómico.
- **Schemas:**
  - `VentaUpdateIn`: mismos campos que `VentaIn`, con `tarjeta`/`cbu` opcionales y validador contextual.
  - `VentaOut`: respuesta completa con desglose e instrumento enmascarado.
- **API:**
  - `PUT /api/ventas/{id}` → `200 VentaOut`.
  - `404` inexistente, `409` aprobada, `422` validación.
- **Web:**
  - `GET /ventas/{id}/editar` renderiza `wizard.html` con `modo_edicion=True`, `venta` y `planes`.
  - `wizard.js` detecta el modo, precarga estado, oculta el formulario de alta y usa `PUT`.
  - El resumen y comprobante muestran el instrumento enmascarado.
- **Integridad:** al reemplazar adherentes se eliminan los anteriores y se insertan los nuevos dentro de la misma transacción; si falla, rollback total.
- **Migración:** no requiere columnas nuevas; usa las de F14.
- **R5:** la venta editada conserva la validación de precio e instrumento; la auditoría se ejecuta nuevamente.

## Tests y casos borde

- Editar adherentes: agregar, eliminar y cambiar datos; el total se recalcula.
- Cambiar de plan y de medio de pago; se aplica el descuento correcto.
- Cambiar tarjeta → CBU y viceversa; se reemplazan los metadatos.
- Venta observada: se corrigen los errores y queda pendiente.
- Venta aprobada: `409`, sin cambios.
- Venta inexistente: `404`.
- Fallo de commit: no quedan adherentes ni cambios parciales.
- Payload inválido: `422` y estado original intacto.
